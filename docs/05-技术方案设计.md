### 1.2 一个关键的架构决策：引擎放哪？

这是本方案最需要想清楚的问题。有两个选项：

**方案甲：规则匹配在 Service Worker 做**
```
页面请求 → MAIN hook → postMessage 问 SW「这个要 mock 吗」→ SW 回答 → 返回
```

**方案乙：规则全量下发给 MAIN world，就地匹配** ← **我们选这个**
```
SW 启动时把规则推给 MAIN → 页面请求 → MAIN 本地匹配 → 直接返回
```

**为什么选乙：**

| 维度 | 甲（SW 匹配） | 乙（MAIN 本地匹配） |
| --- | --- | --- |
| **同步性** | ❌ 致命问题：`XHR.send()` 是同步方法，没法「等」一个异步消息回来 | ✅ 本地匹配是同步的 |
| 延迟 | 每个请求多一次跨进程往返（几 ms～几十 ms） | 无 |
| SW 生命周期 | ❌ SW 被杀时请求会卡住或漏拦 | ✅ 不受影响 |
| 规则同步 | 天然一致 | 需要处理下发时机（见 5.4） |

> **同步性是决定性的。** `xhr.send()` 调用后必须立即决定是放行还是拦截，如果要等一个 `postMessage` 往返，代码没法写（除非改成同步 XHR，那会卡死页面）。所以**引擎必须在 MAIN world 本地持有规则**。
>
> 这也是为什么 core 模块要设计成「纯 TS、零 chrome API 依赖」—— **同一份匹配逻辑要同时跑在 SW 和 MAIN world 两个地方**。

## 2. 规则数据模型（Schema）

> 这一章是整个系统的地基。Schema 定错了，后面所有代码都要返工，AI 也生成不出对的规则。

### 2.1 设计目标

| # | 目标 | 为什么 |
| --- | --- | --- |
| G1 | **自解释** | AI 要能看着 Schema 直接生成规则（L0 需求），字段名必须一眼能懂 |
| G2 | **可版本化演进** | 带 `schemaVersion`，未来加字段不能让老规则失效（A2 要求） |
| G3 | **序列化友好** | 要能存 storage、导出 JSON、走 postMessage —— 所以**不能有函数、不能有 undefined、不能有循环引用** |
| G4 | **区分虚拟与覆盖** | F22 需求 |
| G5 | **可扩展到 V1/V2** | 现在不做的功能（动态响应、延迟、外壳模板），字段位置要预留好，别到时候改结构 |

### 2.2 完整 Schema

```typescript
/** 存储根对象 —— chrome.storage.local 里就存这一个 key */
interface MockStore {
  schemaVersion: 1;              // ← A2：版本化的核心
  enabled: boolean;              // 全局总开关（F4）
  rules: Rule[];
  groups: Group[];
  shellTemplates: ShellTemplate[];  // 响应外壳模板库（F24，V1 用，MVP 先建空数组）
  settings: Settings;
}

/** 单条规则 */
interface Rule {
  id: string;                    // nanoid，永不复用
  name: string;                  // 人类可读，如「商品列表-空数据」
  enabled: boolean;              // 单条开关（F4）
  groupId: string | null;        // 所属分组（V1 的 F13 用；MVP 恒为 null）

  /** 关键：这条规则是覆盖已有接口，还是凭空造一个接口 */
  kind: 'override' | 'virtual';  // ← F22

  match: MatchCondition;
  response: ResponseSpec;

  /** 元信息，不参与匹配 */
  meta: {
    createdAt: number;
    updatedAt: number;
    source: 'manual' | 'capture' | 'ai' | 'import';  // 从哪来的，用于统计和调试
    hitCount: number;            // 命中次数，UI 上展示，帮你发现「配了但从没生效」的规则
    lastHitAt: number | null;
  };
}

/** 匹配条件 */
interface MatchCondition {
  urlMode: 'contains' | 'wildcard' | 'regex';   // F2 三种模式
  url: string;                   // 按 urlMode 解释
  methods: HttpMethod[];         // 空数组 = 匹配所有 method
  /** 域名作用域（F15，V1 用）。空数组 = 所有域名 */
  hosts: string[];
}

type HttpMethod = 'GET' | 'POST' | 'PUT' | 'DELETE' | 'PATCH' | 'HEAD' | 'OPTIONS';

/** 响应定义 */
interface ResponseSpec {
  status: number;                // 200 / 404 / 500...
  headers: Record<string, string>;

  /** MVP 只有 static；V1 加 dynamic / mockjs */
  bodyType: 'static' | 'dynamic' | 'mockjs';
  body: string;                  // 永远存字符串！原因见 2.3

  /** 套哪个响应外壳（F24，V1 用；null = 不套壳，body 就是完整响应） */
  shellTemplateId: string | null;

  /** 延迟模拟（F12，V1 用；MVP 恒为 0） */
  delayMs: number;

  /** 特殊行为（F11 场景预设，V1 用） */
  behavior?: 'normal' | 'timeout' | 'networkError';
}

/** 分组（V1 的 F13） */
interface Group {
  id: string;
  name: string;
  enabled: boolean;              // 组开关：关掉则组内规则全部失效
  defaultShellTemplateId: string | null;
}

/** 响应外壳模板（F24） */
interface ShellTemplate {
  id: string;
  name: string;                  // 如「标准 status/message/data」
  builtin: boolean;              // 内置的不可删除
  /** 用 __DATA__ 占位，如：{"status":0,"message":"ok","data":__DATA__} */
  template: string;
}

interface Settings {
  captureEnabled: boolean;       // 是否采集请求流（F5）
  captureMaxCount: number;       // 请求流最多留多少条，默认 200
  aiReadEnabled: boolean;        // MCP 读侧总开关（Q11：默认 true）
  aiHostWhitelist: string[];     // 读侧域名白名单（Q11 的不可关措施）
}
```

### 2.3 几个关键决策的解释

#### 决策一：`body` 为什么永远存字符串，而不是对象？

```typescript
body: string;     // ✅ 我们的选择
body: unknown;    // ❌ 不用
```

**四个理由：**

1. **保真**：JSON 有精度陷阱。`{"id": 12345678901234567890}` 用 `JSON.parse` 会丢精度。存字符串则原样保留，什么时候需要什么时候解析。
2. **兼容非 JSON**：将来要 mock 一段 HTML、XML、纯文本，字符串天然支持。
3. **编辑器友好**：UI 里是个代码编辑器，用户可能写到一半是非法 JSON。存字符串允许「暂存草稿」，存对象则无法表达中间状态。
4. **为 V1 的 dynamic 铺路**：`bodyType: 'dynamic'` 时 `body` 存的是一段 JS 源码字符串。用同一个字段承载，结构不用改。

**代价**：每次用之前要 `JSON.parse`，且要处理解析失败。这个代价我们接受——在 `responder` 里统一处理，只写一次。

#### 决策二：为什么 `MockStore` 只用一个 storage key？

```typescript
// ✅ 我们的做法
chrome.storage.local.set({ mockStore: {...} })

// ❌ 不这么做
chrome.storage.local.set({ rules: [...], groups: [...], settings: {...} })
```

**原因是原子性。** 分成多个 key，一次「新建规则并加入分组」的操作要写两个 key，两次写之间如果 SW 被杀（03 文档 §3.1，30 秒会被杀），就会留下不一致的中间状态——规则存在但分组里没有它。

单 key 单写入，要么全成功要么全失败。

**代价**：每次改一条规则都要读写整个对象。规则量在几百条以内，这个开销可以忽略（storage.local 有 10MB）。

#### 决策三：`kind` 为什么是显式字段，而不是自动推断？

有人会说：虚拟接口不就是「请求会 404 的接口」吗，运行时判断不就行了？

**不行，三个原因：**

1. **判断不了**。我们拦截时**根本不会发出真实请求**（这正是虚拟接口成立的原因，见 02 文档 §1.2），所以永远不知道真实接口存不存在。
2. **UI 要用**。虚拟规则需要显著标记——因为关掉它页面**真的会报错**，而覆盖式只是回到真实数据。这是完全不同的风险等级。
3. **AI 要用**。L0 Skill 里，「新增一个接口」和「改一个接口的返回」是两种不同意图，显式字段让 AI 表达得清楚。

#### 决策四：为什么有 `meta.hitCount`？

这不是统计癖，是**诊断功能**。

注入式 mock 最大的体验问题是「改了不在 Network 面板显示」（01 文档 §2.2C 提到，Ajax Interceptor Tools 官方都特别说明了这点）。用户配了规则不生效时，第一个疑问永远是「是我规则写错了，还是插件坏了？」

`hitCount` 直接回答这个问题：**命中数为 0 = 规则没匹配上（你的 URL 写错了）；命中数 > 0 但页面没变 = 响应内容有问题。** 两种情况的排查方向完全不同。

### 2.4 Schema 版本迁移机制（A2 落地）

```typescript
// core/store/migrate.ts
type Migration = (old: any) => any;

const migrations: Record<number, Migration> = {
  // 1 → 2 的迁移（现在还用不到，先把机制建起来）
  // 2: (s) => ({ ...s, schemaVersion: 2, newField: defaultValue }),
};

export function migrate(raw: any): MockStore {
  if (!raw || typeof raw !== 'object') return createDefaultStore();

  let store = raw;
  let v = store.schemaVersion ?? 0;

  while (v < CURRENT_SCHEMA_VERSION) {
    const next = v + 1;
    const fn = migrations[next];
    if (!fn) {
      // 没有迁移函数说明版本断层，安全起见回退到默认值而不是崩溃
      console.warn(`[mock] 缺少 v${v} → v${next} 的迁移，重置为默认配置`);
      return createDefaultStore();
    }
    store = fn(store);
    v = next;
  }
  return store as MockStore;
}
```

**为什么现在就要建这个机制**（明明还没有 v2）：

因为**第一次需要迁移的时候，往往已经有你辛苦配了几十条规则的存量数据了**。那时候再补机制，要么丢数据，要么临时写一堆兼容代码。现在建，成本是 20 行；将来建，成本是一次数据事故。

同理，`importStore()` 也要走 `migrate()` —— 别人导给你的规则文件可能是旧版本。

## 3. 分层设计（A1–A4 落地）

### 3.1 分层原则

```
┌─────────────────────────────────────────────────┐
│  宿主层 (hosts)                                  │
│  background / content / inject / popup /        │
│  options / devtools                             │
│  ← 只做「适配」：调 chrome API、渲染 UI            │
├─────────────────────────────────────────────────┤
│  core 层                                         │
│  纯 TypeScript，零 chrome.* 依赖，零 DOM 依赖      │
│  ← 所有业务逻辑住在这里                            │
└─────────────────────────────────────────────────┘
```

**铁律：`core/` 里不允许出现 `chrome.`、`window.`、`document.`。**

### 3.2 为什么这条铁律如此重要

不是为了「代码整洁」这种虚的理由，是三个具体的、现在就能看到的收益：

**收益一：同一份匹配逻辑要跑在两个地方**

1.2 节说过，引擎必须在 MAIN world 本地匹配。但 SW 也需要匹配逻辑（比如 DevTools 面板问「这条历史请求会命中哪条规则」）。如果 matcher 里写了 `chrome.storage.get`，它就只能跑在有 chrome API 的地方，MAIN world 用不了。

**收益二：V2 的 MCP Server 要复用（A1 的真正目的）**

MCP Server 是个 **Node 进程**，那里根本没有 `chrome` 对象。如果规则的增删改查逻辑写在 React 组件的事件处理里，MCP 想复用就只能重写一遍——两套逻辑，两套 bug，还会不一致。

```typescript
// ❌ 逻辑写在 UI 里 —— MCP 无法复用
function RuleEditor() {
  const handleSave = async () => {
    const { mockStore } = await chrome.storage.local.get('mockStore');
    if (mockStore.rules.some(r => r.name === name)) { alert('重名'); return; }
    mockStore.rules.push({ id: nanoid(), name, ... });
    await chrome.storage.local.set({ mockStore });
  };
}

// ✅ 逻辑在 core，UI 只是调用者
function RuleEditor() {
  const handleSave = () => dispatch({ type: 'CREATE_RULE', payload: draft });
}
```

**收益三：core 可以脱离浏览器做单元测试**

纯函数、无副作用，`vitest` 直接跑，不需要启动 Chrome、不需要 mock chrome API。规则匹配这种逻辑，测试用例的价值极高（正则、通配符、边界情况一大堆）。

### 3.3 core 模块划分

```
core/
├── types.ts           # 第 2 章的所有类型定义（唯一真相源）
├── schema.json        # JSON Schema，给 AI 和校验用
│
├── store/
│   ├── defaults.ts    # createDefaultStore()、内置外壳模板
│   ├── migrate.ts     # 版本迁移（2.4 节）
│   └── validate.ts    # 规则合法性校验，返回结构化错误
│
├── engine/
│   ├── matcher.ts     # ★ 请求 → 命中哪条规则（纯函数）
│   ├── responder.ts   # ★ 规则 → 响应内容（纯函数）
│   └── shell.ts       # 响应外壳套用（V1）
│
├── command/
│   ├── types.ts       # Command 联合类型（A3）
│   └── reducer.ts     # ★ (store, command) => store  纯函数！
│
└── capture/
    └── ringBuffer.ts  # 请求流环形缓冲（定长，自动淘汰）
```

**三个 ★ 号的模块是整个系统的心脏，且全部是纯函数。**

### 3.4 命令模式（A3 落地）

**所有对规则的修改，只能通过 dispatch 一个 Command。**

```typescript
// core/command/types.ts
export type Command =
  | { type: 'CREATE_RULE'; payload: Omit<Rule, 'id' | 'meta'> }
  | { type: 'UPDATE_RULE'; payload: { id: string; patch: Partial<Rule> } }
  | { type: 'DELETE_RULE'; payload: { id: string } }
  | { type: 'TOGGLE_RULE'; payload: { id: string; enabled: boolean } }
  | { type: 'SET_GLOBAL_ENABLED'; payload: { enabled: boolean } }
  | { type: 'IMPORT_STORE'; payload: { store: unknown; mode: 'replace' | 'merge' } }
  | { type: 'RECORD_HIT'; payload: { ruleId: string } };

// core/command/reducer.ts —— 纯函数，好测得不得了
export function reduce(store: MockStore, cmd: Command): MockStore {
  switch (cmd.type) {
    case 'CREATE_RULE':
      return { ...store, rules: [...store.rules, materializeRule(cmd.payload)] };
    // ...
  }
}
```

**为什么值得引入这层间接（A3 的理由）：**

来源不同的操作，最终必须走同一条路：

```
Popup 点开关      ─┐
Options 编辑规则  ─┤
DevTools 转 Mock  ─┼→ dispatch(Command) → reduce() → 存储 → 广播给所有订阅者
AI 通过 MCP 下发  ─┘        ↑
                    单一入口 = 单一真相 = 单一 bug 面
```

如果没有这层，V2 接 MCP 时会出现「UI 改规则走 A 路径、MCP 改规则走 B 路径」，两条路径的校验、副作用、广播逻辑各写一遍，状态不同步是必然的。

**附带的好处**：Command 是可序列化的对象，天然可以（1）通过 postMessage 传输，（2）记日志做操作审计，（3）实现撤销/重做，（4)将来 MCP 的工具调用可以直接翻译成 Command。

### 3.5 数据流（A4 落地）

```
                    ┌──────────────┐
   dispatch(cmd) ──→│  SW: 单一状态 │──→ storage.local 持久化
                    │   持有者      │
                    └──────┬───────┘
                           │ 变更后广播
              ┌────────────┼────────────┐
              ↓            ↓            ↓
          Popup      DevTools 面板   所有 Tab 的 MAIN world
         (更新UI)      (更新UI)       (更新规则快照)
```

**Service Worker 是唯一的状态持有者。** 其他所有地方都是订阅者，持有的都是只读副本。

**为什么不让各处自己读 storage？** 因为 SW 会被杀（03 §3.1），storage 是异步的，多处并发读写会有竞态——Spike 里已经踩过一次（`background.js` 的 writeQueue）。单一持有者 + 广播，把竞态收敛到一个点。

## 4. 命令协议与消息流

### 4.1 消息类型总表

| 通道 | 方向 | 消息 | 说明 |
| --- | --- | --- | --- |
| `chrome.runtime` | UI → SW | `DISPATCH` | 提交一个 Command |
| `chrome.runtime` | UI → SW | `GET_STATE` | 拉取当前完整 store |
| `chrome.runtime` | SW → UI | `STATE_CHANGED` | 状态变更广播 |
| `chrome.tabs` | SW → content | `RULES_SNAPSHOT` | 规则快照下发 |
| `postMessage` | content → MAIN | `RULES_SNAPSHOT` | 同上，转发 |
| `postMessage` | MAIN → content | `REQUEST_EVENT` | 请求观测事件 |
| `chrome.runtime` | content → SW | `REQUEST_EVENT` | 同上，转发 |
| Port 长连 | DevTools ↔ SW | `SUBSCRIBE_REQUESTS` | 订阅实时请求流 |

### 4.2 为什么请求流用 Port 长连，而规则下发用一次性消息？

| | 规则下发 | 请求流 |
| --- | --- | --- |
| 频率 | 低（用户改规则时才发） | **高**（页面每个请求一条） |
| 方向 | 单向推送 | 单向推送但量大 |
| 生命周期 | 随时可能发生 | 只在 DevTools 打开时需要 |

`sendMessage` 每次调用都有建立/销毁通道的开销，高频场景下不划算。Port 建一次连接持续用，且**关闭时有 `onDisconnect` 事件**——DevTools 一关，SW 立刻知道该停止推送了，不用做无谓的工作。

### 4.3 规则下发时机（关键细节）

MAIN world 的引擎必须在**页面第一个请求发出之前**拿到规则。但 SW 是异步的，来不及怎么办？

```typescript
// inject.ts 的启动逻辑
let rules: Rule[] = [];
let ready = false;
const pendingUrls: string[] = [];   // 规则到达前发生的请求，记下来

// 拿不到规则时的策略：放行（fail-open）
function shouldMock(url: string, method: string): Rule | null {
  if (!ready) {
    pendingUrls.push(url);   // 记录「漏网」，UI 上提示用户刷新
    return null;             // ← 放行，不拦截
  }
  return matchRule(rules, url, method);
}
```

**为什么选择 fail-open（放行）而不是 fail-closed（阻塞等待）？**

- 阻塞等待意味着要把 `xhr.send()` 变成异步的，做不到（1.2 节讲过）
- 放行的后果：早期请求拿到真实数据，页面正常工作，只是 mock 没生效
- 阻塞的后果：页面卡死或请求失败

**放行是安全的降级。** 但必须让用户知道发生了什么——所以记录 `pendingUrls`，在 UI 上显示「有 N 个请求在规则加载前发出，刷新页面可确保全部生效」。

> 这也是「Mock 数据不准时，第一反应是刷新页面」这个经验的技术根源。我们把它显式化，而不是让用户自己猜。

## 5. 拦截引擎设计（core/engine + inject）

### 5.1 匹配器

```typescript
// core/engine/matcher.ts
export interface RequestInfo {
  url: string;       // 已规范化的绝对 URL
  method: HttpMethod;
  host: string;
}

export function findMatchingRule(
  store: MockStore,
  req: RequestInfo
): Rule | null {
  if (!store.enabled) return null;                    // 总开关

  for (const rule of store.rules) {
    if (!rule.enabled) continue;
    if (rule.groupId && !isGroupEnabled(store, rule.groupId)) continue;
    if (!matchHost(rule.match.hosts, req.host)) continue;
    if (!matchMethod(rule.match.methods, req.method)) continue;
    if (!matchUrl(rule.match, req.url)) continue;
    return rule;                                       // 先到先得
  }
  return null;
}

function matchUrl(m: MatchCondition, url: string): boolean {
  switch (m.urlMode) {
    case 'contains':
      return url.includes(m.url);
    case 'wildcard':
      return wildcardToRegExp(m.url).test(url);
    case 'regex':
      return safeRegExpTest(m.url, url);   // 见 5.2
  }
}
```

**决策：为什么是「先到先得」而不是「最长匹配优先」或「优先级字段」？**

- 最长匹配：规则顺序不影响结果，看起来更「智能」，但**用户无法预测和控制**——两条规则谁生效取决于字符串长度，很反直觉。
- 优先级字段：要多维护一个字段，且用户要理解数字大小的含义。
- **先到先得 + 列表可拖拽排序**：所见即所得。列表从上往下就是匹配顺序，想让哪条优先就拖到上面。**用户的心智模型和系统行为完全一致。**

UI 上会显示「这条规则被上面的 XX 规则遮蔽了」的警告（因为这是先到先得唯一的坑）。

### 5.2 正则安全：一个必须处理的坑

用户输入的正则会导致两个问题：

```typescript
function safeRegExpTest(pattern: string, url: string): boolean {
  try {
    // 问题一：非法正则会抛异常。如果不 catch，
    // 会让整个 hook 崩溃 —— 页面所有请求都挂掉！
    return new RegExp(pattern).test(url);
  } catch {
    return false;   // 非法正则视为不匹配
  }
}
```

**问题二是灾难性回溯（ReDoS）**：像 `(a+)+$` 这种正则遇到特定输入会指数级耗时，直接卡死页面。

MVP 的处理：
1. 在 `validate.ts` 里做**静态检测**，发现嵌套量词等危险模式时给 UI 警告（不阻止保存，因为可能是误报）
2. 每次匹配设一个「预算」——如果单次匹配耗时超过 50ms，记一条警告日志并禁用该规则

> 这不是过度设计。引擎跑在**用户的每一个请求**上，任何异常或卡顿都会直接毁掉整个页面。**引擎代码的健壮性要求，比 UI 代码高一个数量级。**

### 5.3 响应构造器

```typescript
// core/engine/responder.ts
export interface MockResponse {
  status: number;
  headers: Record<string, string>;
  body: string;
  delayMs: number;
}

export function buildResponse(rule: Rule, req: RequestInfo): MockResponse {
  const spec = rule.response;
  let body = spec.body;

  // V1：套响应外壳
  if (spec.shellTemplateId) {
    body = applyShell(shellTemplate, body);
  }

  return {
    status: spec.status,
    headers: { 'content-type': 'application/json', ...spec.headers },
    body,
    delayMs: spec.delayMs,
  };
}
```

注意这里**返回的是纯数据，不是 `Response` 对象**。因为：
- `Response` 是浏览器 API，core 层不能依赖（3.1 铁律）
- fetch 和 XHR 需要的响应形态不同（一个要 `Response`，一个要往实例上挂 getter），由各自的宿主适配

### 5.4 注入层（inject.ts）—— Spike 的 E1–E4 落地

Spike 验证出的四条要点，在这里落实：

```typescript
// hosts/inject/index.ts

// ═══ E1：时机不可退让 ═══
// manifest 里必须是 run_at: document_start + world: MAIN
// 这是「坐在调用链最底层」的唯一保证（04 文档 §2）

const originalFetch = window.fetch;
const originalSend = XMLHttpRequest.prototype.send;

window.fetch = function (input, init) {
  const req = normalizeRequest(input, init);
  const rule = shouldMock(req.url, req.method);

  if (!rule) {
    reportObserve(req);
    return originalFetch.apply(this, arguments);
  }

  const res = buildResponse(rule, req);
  reportMock(req, rule);
  return delay(res.delayMs).then(() =>
    new Response(res.body, { status: res.status, headers: res.headers })
  );
};

// ═══ E2：伪装成原生，防监控/风控 SDK 检测篡改 ═══
try {
  Object.defineProperty(window.fetch, 'name', { value: 'fetch' });
  window.fetch.toString = () => originalFetch.toString();
} catch {}
```

**E3 的落地（这条最容易写错）：**

```typescript
// ❌ 错误：用引用相等判断 hook 是否有效
function isHealthy() {
  return window.fetch === ourFetch;   // 你司站点上这里恒为 false！
}

// ✅ 正确：用行为判断
function isHealthy() {
  return hitCountSinceInstall > 0 || observeCountSinceInstall > 0;
}
```

04 文档验证出：你司站点的监控 SDK 会在我们之后包一层，导致 `window.fetch !== ourFetch`。但我们仍在最底层，mock 照常生效。**任何用引用相等做健康判断的代码都会误报。**

### 5.5 XHR 拦截的技术细节

XHR 比 fetch 麻烦，因为 `status`、`responseText` 等都是**原型上的只读 getter**。

```typescript
XMLHttpRequest.prototype.send = function (body) {
  const rule = shouldMock(this.__mockInfo.url, this.__mockInfo.method);
  if (!rule) return originalSend.apply(this, arguments);

  const res = buildResponse(rule, this.__mockInfo);

  // 关键手法：在【实例】上 defineProperty，遮蔽原型上的 getter
  Object.defineProperty(this, 'status', { get: () => res.status, configurable: true });
  Object.defineProperty(this, 'responseText', { get: () => res.body, configurable: true });
  Object.defineProperty(this, 'readyState', { get: () => 4, configurable: true });
  // ...

  // 必须异步派发事件。同步派发会让 axios 等库的状态机错乱
  // （send() 还没返回，onload 就触发了）
  setTimeout(() => {
    this.dispatchEvent(new Event('readystatechange'));
    this.dispatchEvent(new ProgressEvent('load'));
    this.dispatchEvent(new ProgressEvent('loadend'));
  }, res.delayMs || 0);

  // 不调用 originalSend —— 真实请求根本不发出
  // 这正是虚拟接口不会 404、不触发 CORS 预检的原因（02 文档 §1.2）
};
```

> `dispatchEvent` 会同时触发 `addEventListener` 注册的监听和 `onload` 这类属性形式的监听，所以两种写法的业务代码都能正常工作。这一点 Spike 已在真实站点验证过。

## 6. 请求采集与 Capture-to-Mock（F5/F6）

### 6.1 两个数据来源，各有取舍

| 来源 | 能拿到响应体吗 | 覆盖范围 | 何时可用 |
| --- | --- | --- | --- |
| **注入层观测**（我们 hook 到的） | ✅ 能（我们在调用链里） | 仅 fetch/XHR | 总是 |
| `chrome.devtools.network` | ⚠️ 要异步调 `getContent()` | 所有请求（图片、CSS…） | 仅 DevTools 打开时 |

**MVP 用注入层观测作为主来源**，理由：
- 它能直接拿到响应体，而 Capture-to-Mock 的核心价值就是「把真实响应填进编辑器」
- 它不依赖 DevTools 是否打开
- devtools.network 的 `getContent()` 对某些响应类型会返回空

### 6.2 环形缓冲：为什么不用普通数组

```typescript
// core/capture/ringBuffer.ts
export class RingBuffer<T> {
  private items: T[] = [];
  constructor(private capacity: number) {}
  push(item: T) {
    this.items.push(item);
    if (this.items.length > this.capacity) {
      this.items.splice(0, this.items.length - this.capacity);
    }
  }
}
```

一个正常的 SPA 页面，几分钟就能发出上千个请求。如果无限累积：
- storage 会被撑爆（10MB 限制）
- 每次广播给 DevTools 的数据量线性增长，UI 卡顿

定长 200 条，够用且可控。

**存 `session` 而不是 `local`**（03 文档 §7.1）：请求流是临时数据，浏览器关了就该清空，没有持久化的必要。

### 6.3 响应体截断

```typescript
const MAX_BODY_SIZE = 256 * 1024;   // 256KB

function truncateBody(body: string) {
  if (body.length <= MAX_BODY_SIZE) return { body, truncated: false };
  return { body: body.slice(0, MAX_BODY_SIZE), truncated: true };
}
```

有些接口返回几 MB 的数据。全存下来会撑爆 storage，且 Capture-to-Mock 时也不可能让你在编辑器里改一个 5MB 的 JSON。截断并标记，UI 上提示「响应体过大已截断，转为 Mock 后需手动补全」。

### 6.4 Capture-to-Mock 的转换逻辑（F6，D1 差异化的核心）

```typescript
export function captureToRuleDraft(entry: CapturedRequest): RuleDraft {
  const u = new URL(entry.url);
  return {
    name: suggestName(u),                   // 从路径猜个名字，如「/api/goods/list」
    kind: 'override',                       // 从抓包来的一定是覆盖式
    enabled: true,
    match: {
      urlMode: 'contains',
      url: u.pathname,                      // ← 关键：只取 path，不含 query
      methods: [entry.method],
      hosts: [u.host],
    },
    response: {
      status: entry.status,
      headers: {},
      bodyType: 'static',
      body: prettyJson(entry.responseBody), // 格式化后填进编辑器
      shellTemplateId: null,
      delayMs: 0,
    },
    meta: { source: 'capture' },
  };
}
```

**为什么默认只取 `pathname`，丢掉 query？**

这是个小决策，但直接影响 F6 的「≤3 次点击」目标能否达成。

抓到的 URL 是 `/api/goods/list?page=1&size=20&t=1690000000`。如果原样作为匹配条件：
- 用户翻到第 2 页，`page=2`，规则不匹配了 → mock 失效
- 很多接口带时间戳防缓存，每次都不同 → 规则永远只命中一次

用 `pathname` 匹配，覆盖该接口的所有调用，符合 90% 的意图。需要按参数区分的场景留给 V2 的 F21。

### 8.3 一个构建上的坑

**注入脚本不能被打包成 ES module。** MAIN world 的脚本以普通 script 方式执行，用 `import` 会报错。CRXJS 对 content script 会自动处理，但要确认 `inject` 入口打包成 IIFE 格式。

同时，**core 的代码会被同时打进 SW 和 inject 两个 bundle**，这是预期行为（1.2 节说过匹配逻辑要跑两个地方），不是重复打包的 bug。

## 9. L0 AI Skill 设计

### 9.1 Skill 要解决的问题

让你能对 AI 说「帮我 mock 一个商品列表接口，10 条数据带分页」，AI 生成的规则 JSON 能被插件直接导入。

### 9.2 关键：Skill 的质量取决于 Schema 的质量

02 文档说过，L0 是「Schema 设计质量的试金石」。具体来说，AI 生成规则时最容易错的地方：

| 易错点 | Schema 侧的应对 |
| --- | --- |
| 不知道该用 `override` 还是 `virtual` | 字段名本身自解释，Skill 里给明确判断标准 |
| `body` 该填对象还是字符串 | Schema 注释写明「永远是字符串」，Skill 给示例 |
| 不知道有哪些外壳模板 | Skill 里说明「先问用户，或用 shellTemplateId: null」 |
| 生成了 `id`、`meta` 等系统字段 | Skill 明确说明这些由插件生成，不要填 |

### 9.3 Skill 内容结构

```
skills/mock-rule-authoring/
├── SKILL.md              # 主文档：何时触发、生成流程、注意事项
├── schema.json           # 从 core/schema.json 同步（构建时自动拷贝）
└── examples/
    ├── virtual-list.json      # 虚拟接口：分页列表
    ├── override-empty.json    # 覆盖式：改成空数据
    └── error-500.json         # 错误场景
```

**构建时自动同步 schema.json**，避免 Skill 和代码里的 Schema 漂移——这是个很容易发生的问题，手动同步一定会忘。

### 9.4 导入路径

插件 Options 页加一个「从剪贴板导入」按钮：读剪贴板 → `migrate()` → `validate()` → 预览差异 → 确认导入。

**必须有预览步骤。** AI 生成的东西不能盲信，让你看一眼「将新增 3 条规则、修改 1 条」再确认。

### 10.1 为什么 S2 强调测试先行

matcher 是唯一一个「逻辑复杂 + 纯函数 + 出错后果严重」的模块：
- 三种匹配模式 × 边界情况（空 URL、特殊字符、大小写、端口号、hash）组合很多
- 它跑在用户每个请求上，错了就是整站异常
- 纯函数，测试成本极低

这是投入产出比最高的测试。其他模块（UI、消息传递）不强求。

## 12. 附：设计决策速查

| 决策 | 选择 | 核心理由 |
| --- | --- | --- |
| 引擎位置 | MAIN world 本地匹配 | `xhr.send()` 是同步的，等不了跨进程消息 |
| `body` 类型 | 永远是 string | 保真、兼容非 JSON、支持草稿、为 dynamic 铺路 |
| storage 结构 | 单一 key | 原子性，避免 SW 被杀导致的中间状态 |
| `kind` 字段 | 显式存储 | 运行时推断不出来（我们不发真实请求） |
| 匹配优先级 | 先到先得 + 拖拽排序 | 所见即所得，用户可预测 |
| 状态持有者 | Service Worker 唯一 | 收敛并发竞态到一个点 |
| 修改入口 | dispatch(Command) | UI 和 MCP 走同一条路（A3） |
| 规则未就绪 | fail-open 放行 | 阻塞会卡死页面；放行是安全降级 |
| hook 健康判断 | 行为判断，非引用相等 | 04 文档验证：站点会包裹我们 |
| 请求流存储 | storage.session + 环形缓冲 | 临时数据，且要防撑爆 |
