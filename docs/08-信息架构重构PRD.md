## 0. 问题诊断

### 0.1 用户反馈

1. 场景卡片难看（排版错乱）
2. **「我不太理解场景和分组的区别，这俩不是同一个意思吗」**
3. 规则全堆在一起，多了不好管
4. 希望有项目层级、关联域名、分页管理

### 0.2 第 2 条是设计缺陷，不是理解问题

我把「场景」实现成了「互斥分组」，于是它和普通分组在界面上长得一模一样 ——
都是一个装规则的框，都有个开关，都能折叠。

**两者的差别只体现在行为上（单选 vs 多选），而行为差异撑不起两个名字。**
用户看到两个长得一样的东西却叫不同名字，只会困惑。

真正的问题是：这两个概念本来就**不该是同一类东西**。

| | 本质 | 规则与它的关系 |
| --- | --- | --- |
| **分组** | 容器 | 规则**住在**分组里，一条规则只属于一个分组 |
| **场景** | 状态快照 | 场景**引用**规则，一条规则可被多个场景引用 |

分组回答「这条规则属于哪个模块」，场景回答「现在哪些规则该开着」。
一个是**归属**，一个是**状态**，是两个正交的维度。

**结论**：场景必须在视觉上彻底离开列表 —— 它不是列表里的一个框，
而是顶栏的一个模式选择器。这样一眼就能看出它是另一类东西。

## 1. 新的信息架构

```
项目 Project              绑定域名，是「哪个前端应用」的边界
 └── 分组 Group           业务模块归类，纯粹的文件夹
      └── 规则 Rule       具体的 mock

场景 Scenario             ← 正交轴，不在这个树里
                            记录「哪些规则处于启用」的快照
```

### 1.1 三层容器

| 层级 | 必需？ | 职责 | 关键属性 |
| --- | --- | --- | --- |
| **项目** | 可选 | 按前端应用划分工作空间 | **绑定域名**（白/黑名单） |
| **分组** | 可选 | 按业务模块归类规则 | 组开关 |
| **规则** | 必需 | 实际的 mock 定义 | — |

**"可选"的含义**：规则可以直接放在项目下不进分组；分组也可以不属于任何项目
（放在「全局分组」区）。不强制用户先建项目才能用 —— 新用户第一次用只想 mock 一个接口。

### 1.2 项目为什么值得成为独立一层

如果项目只是「更大的分组」，那就没必要存在。它的独特价值是**绑定域名**：

```
项目「金链运营平台」
  域名：dev2.glink.jd.com, test-glink.jd.com
  → 项目内所有规则自动限定在这些域名下生效
```

这解决一个真实痛点：同一个 `/api/user/info` 路径，在 A 系统和 B 系统含义完全不同。
现在每条规则都要单独填 hosts，有了项目就只配一次。

同时它也让「切换项目」变成一个有意义的动作 —— 你今天在做 A 系统，
就只看 A 系统的规则，不被 B 系统的几十条规则干扰。

### 1.3 域名匹配规则

```typescript
interface ProjectHostScope {
  mode: 'include' | 'exclude';   // 白名单 / 黑名单
  patterns: string[];             // 支持 * 通配，如 *.glink.jd.com
}
```

| 模式 | 语义 |
| --- | --- |
| `include`（默认） | 只在列出的域名下生效 |
| `exclude` | 除列出的域名外都生效 |

**优先级**：规则自己的 `match.hosts` 若非空，覆盖项目设置（少数派例外场景）。

## 2. 场景重新定义

### 2.1 它是什么

**场景 = 一份「哪些规则处于启用状态」的快照。**

不是容器，不装规则，不出现在列表树里。

```
场景「全空态」
  → 启用：商品列表-空、订单列表-空、消息列表-空
  → 停用：其他所有规则
```

同一条规则可以同时被「全空态」和「弱网测试」引用 —— 这在旧的互斥分组模型里做不到，
因为规则只能属于一个分组。**这也再次说明它俩不是一类东西。**

### 2.2 它在界面上的位置

**顶栏的模式选择器**，和总开关并排。永远可见，一眼知道当前处于什么状态。

```
Mock Studio    项目 [金链运营平台 ▾]    场景 [全空态 ▾]    ● 已启用
```

### 2.3 操作

| 操作 | 说明 |
| --- | --- |
| 切换场景 | 立即批量应用该场景记录的启用状态 |
| 保存当前状态为场景 | 把此刻的开关状态存成一个新场景 |
| 更新场景 | 用当前状态覆盖已有场景 |
| 「未使用场景」 | 默认状态，手动开关规则时自动切到这里，不会污染已存的场景 |

**关键交互细节**：切到某场景后又手动改了开关，顶栏应显示「全空态 · 已修改」，
并提供「保存」或「还原」。不能让用户以为自己还在纯净的场景里。

## 3. 布局设计

### 3.1 三栏结构

```
┌──────────────────────────────────────────────────────────────────────┐
│  顶栏：品牌 · 项目选择 · 场景选择 · 总开关                              │
├────────────┬─────────────────────────────────────┬───────────────────┤
│            │                                     │                   │
│  侧栏      │  主区                                │  编辑器           │
│  240px     │  分组 + 规则列表（分页）              │  可拖拽调宽        │
│            │                                     │  按需出现          │
│  项目列表  │                                     │                   │
│  全局分组  │                                     │                   │
│            │                                     │                   │
├────────────┴─────────────────────────────────────┴───────────────────┤
│  底栏：统计 · 分页器                                                   │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.2 视觉原则（"简洁又有高级感"的具体落地）

当前界面的问题是**框太多**：每个分组一个框，每条规则一个框，框里套框，
视觉噪音大，层级反而看不清。

新设计遵循四条：

| # | 原则 | 具体做法 |
| --- | --- | --- |
| 1 | **用留白和字号建立层级，而不是边框** | 分组标题去掉外框，靠字重 + 上方留白区分；规则行只用一条极淡的分隔线 |
| 2 | **克制用色** | 中性灰为主，蓝色只用于「当前选中」和主操作；状态色（虚拟橙 / MOCK 绿）只出现在小徽标上 |
| 3 | **降低静息状态的信息密度** | 操作按钮默认隐藏，hover 才出现；次要信息（URL、命中数）用更小字号和更淡的颜色 |
| 4 | **对齐** | 所有行左侧对齐到同一条基线，复选框、徽标、名称各占固定列宽 |

### 3.3 侧栏

```
┌──────────────────────────┐
│  搜索项目…                │
├──────────────────────────┤
│  项目                  ＋ │
│                          │
│  ● 金链运营平台      12   │  ← 当前项目，左侧色条
│    dev2.glink.jd.com     │  ← 绑定域名，小字
│                          │
│    支付中台           8   │
│    pay.jd.com            │
│                          │
│    活动页             3   │
│                          │
│  ‹ 1 / 2 ›               │  ← 项目多时分页
├──────────────────────────┤
│  全局分组              ＋ │  ← 不属于任何项目
│    通用错误码         4   │
├──────────────────────────┤
│  未归档               5   │
└──────────────────────────┘
```

### 3.4 主区

```
金链运营平台                                    ⚙ 项目设置
dev2.glink.jd.com · test-glink.jd.com

[+ 新建规则]  [+ 分组]   搜索…            [全部 ▾] [仅启用 ▾]

──────────────────────────────────────────────────────
  商品模块                                    3 条  ⋯
──────────────────────────────────────────────────────
  ☑  覆盖   商品列表                        12 次
     /api/goods/list · POST · 200
  ☑  覆盖   商品详情                         4 次
     /api/goods/detail · GET · 200
  ☐  虚拟   库存查询                         0 次
     /api/stock/query · GET · 200

──────────────────────────────────────────────────────
  订单模块                                    2 条  ⋯
──────────────────────────────────────────────────────
  …

──────────────────────────────────────────────────────
  未分组                                      5 条
──────────────────────────────────────────────────────
  …

                              共 42 条   ‹ 1 2 3 › 20/页
```

分组标题不再是一个框，而是一条**带上方留白的分隔标题**。这样滚动时层级依然清晰，
但视觉噪音大幅降低。

### 3.5 分页策略

| 位置 | 策略 | 理由 |
| --- | --- | --- |
| 项目列表 | 超过 8 个分页 | 侧栏空间有限 |
| 规则列表 | 默认 20/页，可选 50/100 | 用户明确要求 |
| 分组 | **不分页** | 分组是标题不是条目，分页会把同组规则切断，反而难用 |

**注意**：分页按「规则」分，跨分组连续排。若某页只包含某分组的部分规则，
标题会标注「商品模块（3/8）」，避免误以为组内只有这几条。

## 4. 数据模型变更

```typescript
interface Project {
  id: string;
  name: string;
  /** 绑定域名 —— 项目存在的核心理由 */
  hostScope: {
    mode: 'include' | 'exclude';
    patterns: string[];
  };
  /** 项目级默认响应外壳，新建规则时自动带上（接上一直没用的字段） */
  defaultShellTemplateId: string | null;
  order: number;
}

interface Group {
  id: string;
  name: string;
  enabled: boolean;
  /** 所属项目。null = 全局分组 */
  projectId: string | null;
  collapsed: boolean;
  defaultShellTemplateId: string | null;
  // ❌ 移除 exclusive —— 场景不再是分组的一种
}

interface Rule {
  // …现有字段
  groupId: string | null;
  /** 冗余存一份，便于「规则不在任何分组但属于某项目」的情况 */
  projectId: string | null;
}

interface Scenario {
  id: string;
  name: string;
  /** 所属项目。null = 全局场景 */
  projectId: string | null;
  /** 该场景下应启用的规则 id 集合 */
  enabledRuleIds: string[];
}

interface MockStore {
  schemaVersion: 2;        // ← 结构变了，必须升版本
  projects: Project[];
  groups: Group[];
  rules: Rule[];
  scenarios: Scenario[];
  activeProjectId: string | null;
  activeScenarioId: string | null;
  // …
}
```

### 4.1 迁移（v1 → v2）

现有数据必须无损升级，用户不能丢规则：

| v1 | v2 |
| --- | --- |
| 普通分组 | 原样保留，`projectId: null`（全局分组） |
| **互斥分组** | **转成 Scenario**，其成员规则 id 存进 `enabledRuleIds`；原分组降级为普通分组 |
| 规则 | 补 `projectId: null` |
| — | 不自动创建项目，保持「未归档」状态，由用户自行整理 |

**互斥组转场景是有损的**（规则原本属于该组，转换后归属会变），
所以迁移时要在 UI 上给出一次性提示，说明发生了什么。

## 5. 关键交互

### 5.1 首次使用不该看到空的三层结构

新用户打开只有一个「未归档」区和一个「新建规则」按钮。
项目和分组都是**用到了再建**，不做前置要求。

### 5.2 切换项目

- 主区只显示该项目的分组与规则
- DevTools 面板的请求流按项目域名过滤（可关）
- 场景下拉只显示该项目的场景 + 全局场景

### 5.3 规则归属调整

| 方式 | 场景 |
| --- | --- |
| 拖拽 | 同一视图内快速调整 |
| 编辑器下拉 | 精确指定项目 + 分组 |
| 批量选择 | 多选规则后统一移动（新增） |

### 5.4 域名冲突提示

规则的 `match.hosts` 与所属项目的 `hostScope` 冲突时，
编辑器给出提示：「本规则限定 a.com，但项目「X」只在 b.com 生效，两者无交集，规则不会命中」。

这类「配了但永远不生效」的问题必须显式暴露 —— 和现有的遮蔽检测、命中数是同一类诊断。
