| 需求 | 可行性 | 成本 | 建议排期 |

| **虚拟接口**（凭空新增后端不存在的接口） | ✅ 完全可行 | **引擎侧接近零成本**，成本全在 UI 和使用体验 | **进 MVP** |

## 1. 需求 A：虚拟接口（Virtual Endpoint）

### 1.1 概念澄清

我们要区分两类 Mock，它们的使用路径完全不同：

| 类型 | 定义 | 典型场景 | 起步路径 |
| --- | --- | --- | --- |
| **覆盖式 Mock**（Override） | 接口真实存在，只改它的响应 | 想看空状态、想造错误、想改某个字段 | Capture-to-Mock（抓包一键转） |
| **虚拟接口**（Virtual） | 后端**根本没有**这个接口 | 后端还没开发；接口文档刚定；纯前端先跑通 | **必须手工新建**（没东西可抓） |

### 1.2 技术判断：为什么虚拟接口几乎是"免费"的

因为路线 B（注入 hook）是在 `fetch` / `XHR` **被调用的那一刻**就拦截并直接 resolve 的，**真实请求从未发出**。所以：

- ✅ 不会有 404 / 502
- ✅ 不会有 CORS 预检（OPTIONS）失败
- ✅ 不需要后端存在，甚至不需要域名能解析
- ✅ 不需要为它单独写引擎逻辑——命中规则就返回，和覆盖式走同一条路

> 顺带说明：这一点**反过来加强了第 01 号文档里选择路线 B 的正确性**。如果走 declarativeNetRequest（路线 A），因为它改不了响应体，虚拟接口只能靠重定向到 data URL 硬凑，做不动态、也处理不好 CORS。**虚拟接口这个需求，直接排除了 A 作为主路线的可能。**

### 1.3 但有三个必须处理的差异

| # | 差异 | 对策 |
| --- | --- | --- |
| 1 | **没有真实请求可抓**，Capture-to-Mock 路径失效 | 必须提供一条同样顺畅的「手工新建」路径。这条路径的体验就是这个功能的全部——见 F23 模板脚手架 |
| 2 | **插件一关，页面真的会报错**（404 或跨域），而覆盖式 Mock 关掉只是回到真实数据 | UI 上明确标记为「虚拟」（不同颜色/图标）；关闭总开关时，若存在启用中的虚拟规则要给出提示 |
| 3 | **Network 面板连一条失败记录都没有**，完全不可观测 | F5 实时请求面板是虚拟接口的**唯一**可观测手段。面板里要能看到「虚拟接口 /api/xxx 被调用了 3 次」 |

### 1.4 新增功能

| ID | 功能 | 说明 | 排期 |
| --- | --- | --- | --- |
| **F22** | **虚拟接口** | 新建规则时选择「覆盖已有接口 / 新建虚拟接口」；虚拟规则独立标记与统计 | **MVP** |
| F23 | **接口模板脚手架** | 一键生成常见结构：分页列表 / 详情 / 增删改统一返回 / 空数据。不用从空白 JSON 开始写 | V1 |
| **F24** | **响应外壳模板库** | 见 1.5 节（设计已按 Q12 反馈修订） | V1 |
| **F25** | **外壳自动推断** | Capture-to-Mock 时从真实响应自动识别外壳，把 `data` 部分挑出来给你编辑 | V1 |

### 1.5 响应外壳：模板库而非全局配置（按 Q12 修订）

**原设计有误**。最初把响应外壳设计成「全局配一次」，前提是公司响应格式统一。实际情况是：

> 大多数是 `{ status, message, data }`，但经过风控或其他中间层转换后又会变成别的格式。

所以外壳**不是一个值，是一组值**，且哪个规则用哪个壳是不确定的。修订后的设计：

| 层次 | 设计 |
| --- | --- |
| **内置模板** | 预置几个高频格式，开箱即用：`{status, message, data}`、`{code, data, message}`、`{success, result}`、`{errno, errmsg, data}`、**裸数据**（无外壳） |
| **自定义模板** | 用户可新建并命名保存自己的外壳，用 `__DATA__` 占位符标记数据插入点。风控层那种变体就靠这个 |
| **作用域** | **规则级选择**用哪个模板（不是全局唯一）；分组/域名可设默认模板，新建规则时自动带上，但可覆盖 |
| **自动推断（F25）** | Capture-to-Mock 抓到真实响应时，自动比对模板库识别出用的是哪个壳；识别不出就提示「另存为新模板」——**用着用着模板库就自己长齐了** |

> F25 是这里最值钱的一条：它把「维护模板库」这件苦差事变成了副产品。你只管抓包配 mock，模板库自动积累。

> 对 AI 协同的影响：模板库同样要暴露给 MCP（`list_shell_templates`），否则 AI 生成规则时不知道该套哪个壳。

## 2. 需求 B：AI 协同

### 2.1 这个需求改变了产品定位

原定位：

> 一个不需要登录、不写代码、从抓到的真实请求一键起步的前端 Mock 插件。

修订后：

> **一个 AI 可编程的本地 Mock 运行时** —— 人可以点，AI 也可以直接写。

新增第四条差异化主张：

| # | 主张 | 说明 |
| --- | --- | --- |
| **D4** | **AI-Native**：Mock 规则是 AI 的一等公民，AI 既能**读**到页面实际发生了什么请求，也能**写**规则 | 现有 mock 工具全部是「给人用的 GUI」，没有一个把自己暴露成 AI 可调用的能力 |

### 2.2 三级渐进方案

不建议一步到位做 MCP。按成本/价值排，分三级：

---

#### **L0：Skill + 剪贴板导入**（MVP 就能有，成本 ≈ 0）

**做法**：写一个 Claude Code Skill，内容是「本插件的规则 Schema + 生成规范 + 若干示例」。

**用法**：

```
你：帮我 mock 一个商品列表接口，10 条数据，带分页
AI：（按 Schema 生成规则 JSON）
你：在插件里点「从剪贴板导入」→ 生效
```

**前提条件**（这就是它的真正价值）：规则 Schema 必须是**稳定、自解释、JSON Schema 化**的。

**为什么建议 MVP 就做**：
- 成本只有「一个 Schema 文档 + 一个 skill 文件 + 插件里一个粘贴导入按钮」
- 它是 Schema 设计质量的**试金石**——如果 AI 按 Schema 生成的规则总是不对，说明 Schema 设计有问题，这个反馈在 MVP 阶段拿到远比 V2 才发现便宜

---

#### **L1：规则文件进 Git**（价值明确，但实现有坑）

**设想**：插件绑定项目里的 `.mock/` 目录，AI 直接写文件，插件自动加载。规则跟着 git 分支走。

**价值**：★★★★☆ —— mock 规则进版本库、跟分支切换、团队共享，这解决了 P6。

**实现上的坑**（必须说清楚）：
- File System Access API **在 Service Worker 里不可用**，需要用户手势触发 `showDirectoryPicker`
- 目录句柄可存 IndexedDB 持久化，但**没有 watch API**，只能轮询
- 轮询需要一个存活的页面上下文（DevTools 面板 / offscreen document）

**建议**：**不单独做 L1**。它的核心价值（规则进 git）可以由 L2 的 MCP Server 顺带实现——MCP Server 本来就是个 Node 进程，读写项目目录对它是天然能力。把 L1 的价值并入 L2，避免造两套同步机制。

---

#### **L2：MCP Server + WebSocket Bridge**（V2 主线）

**架构**（三段式，`browser-tools-mcp` 等项目已验证）：

```
  Claude Code / Cursor
        ↕  stdio (MCP 协议)
  mock-mcp-server  (Node 进程)
        ↕  WebSocket (localhost:随机端口)
  Chrome 插件 Service Worker
        ↕  chrome.runtime 消息
  注入层（实际执行拦截）
```

**关键技术点**：

| 点 | 说明 |
| --- | --- |
| 谁连谁 | **插件作为 WS client 主动连 localhost**。插件里起不了 server，只能这样 |
| SW 存活 | Chrome 116+ 起 **WebSocket 活动会重置 SW 的 30s 空闲计时器**；仍需 20s 心跳兜底；manifest 声明 `minimum_chrome_version: "116"` |
| 兜底方案 | 若长连仍不稳，改由 **offscreen document** 持有 WebSocket，它不受 SW 生命周期限制 |
| 规则进 git | MCP Server 负责读写项目里的 `.mock/*.json`，同时通过 WS 推给插件（吸收 L1 的价值） |

**MCP 工具集设计**（真正的价值在读侧）：

*写侧：*
- `create_mock` / `update_mock` / `delete_mock`
- `create_virtual_endpoint`
- `toggle_mock` / `activate_scenario`

*读侧 —— 这才是杀手锏：*
- `list_recent_requests` — **让 AI 看到页面实际发了哪些请求**
- `get_request_detail` — 拿到真实的响应结构（或 404 事实）
- `list_shell_templates` — 拿到响应外壳模板库，AI 才知道该给数据套哪个壳（见 1.5 节）

**为什么读侧是关键——这是 vibe coding 的完整闭环**：

```
AI 写完前端代码，你打开页面，没数据。
你：「页面没数据，帮我 mock 一下」

AI → list_recent_requests   看到页面在请求 /api/goods/list，返回 404
AI → get_request_detail     确认请求参数是 { page, size, keyword }
AI → create_virtual_endpoint 造一个贴合参数结构的分页响应
你刷新页面 → 有数据了

全程你只说了一句话，没有手抄 URL，没有写 JSON。
```

**这个闭环，现有任何 mock 工具都做不到**——因为它们都只是 GUI，AI 看不见里面发生了什么。

### 2.3 安全设计（开了 localhost 口子就必须做）

| 风险 | 对策 |
| --- | --- |
| localhost WS 端口**被任意网页连接**并操控你的 mock | 首次连接需**配对码**（插件 UI 显示 6 位码，MCP 端填入）；校验 `Origin`；端口随机化 |
| 抓到的请求含 **token / Cookie / 个人数据**被送给 AI | **默认脱敏**：`Authorization` / `Cookie` / `Set-Cookie` 一律打码；**域名白名单**——只有白名单内的请求对 MCP 可见；提供「读侧总开关」，默认关闭 |
| AI 误删规则 | 删除类工具需二次确认；提供回收站 |
| MCP 越权拿到通用浏览器能力 | 工具集**严格限定在 mock 域**，绝不暴露通用 JS 执行或任意页面读取 |

> 特别提示：读侧能力（让 AI 看到真实请求）价值最大，风险也最大。公司接口的请求头里往往有真实鉴权凭证。**建议读侧默认关闭，用时手动开，且强制脱敏不可关。**

## 3. 对原方案的影响（最重要的一节）

### 3.1 架构必须从第一天就预留（否则 V2 要大改）

即使 MVP 不做 MCP，以下四条**必须在 MVP 就做对**：

| # | 预留项 | 说明 | 不做的后果 |
| --- | --- | --- | --- |
| A1 | **规则 CRUD 抽成独立 core 模块** | UI 只是它的一个消费者，MCP 是另一个消费者。业务逻辑不许写在 React 组件里 | V2 时 MCP 无法复用，要把逻辑从 UI 里抠出来重写 |
| A2 | **规则 Schema 从一开始 JSON Schema 化 + 版本化**（带 `schemaVersion` 字段） | AI 要按它生成规则；未来 Schema 演进要能迁移 | AI 生成的规则不可靠；老规则升级即失效 |
| A3 | **命令模式统一入口**：所有规则变更走同一个 `dispatch(command)` | UI 发的命令和 WS 桥接上来的命令走同一条路，天然一致 | 两套路径两套 bug，状态会不同步 |
| A4 | **抓到的请求进统一 store** | UI 的请求面板和 MCP 的 `list_recent_requests` 共用一份数据 | 读侧要重新实现一遍采集 |

这四条不增加 MVP 的功能量，**只是要求写代码时分层分对**。对你来说这反而是好事——「怎么给插件分层」本身就是这个项目该学到的东西。

### 3.2 非目标是否需要修订

原文 4.3 节写「不做云同步、不做账号体系」——**继续有效**。MCP 是**本地进程**，不违背「本地优先、零账号」的主张。反而更强化了它：**AI 能力也在本地，数据不出机器。**

### 3.3 修订后的路线图

| 阶段 | 内容 | 相比原方案的变化 |
| --- | --- | --- |
| **MVP** | F1–F8 + **F22 虚拟接口** + **L0 Skill** + **A1–A4 架构预留** | 净增 1 个功能 + 1 个 skill 文件 + 分层要求 |
| **V1** | F9–F15 + **F23 模板脚手架** + **F24 外壳模板库** + **F25 外壳自动推断** | 净增 3 个功能 |
| **V2** | **L2 MCP Server（主线）** + 原 F16–F21 | MCP 从「没有」提升为 V2 主线 |

### 3.4 学习价值增量

新需求带来的额外知识点，**含金量很高**：

| 来源 | 知识点 |
| --- | --- |
| L2 长连接 | **Offscreen Document**（MV3 的重要逃生舱）、Service Worker 生命周期实战、WebSocket in SW |
| L2 架构 | 跨进程架构设计、命令模式、本地服务鉴权 |
| MCP | **MCP 协议本身**、如何把一个工具暴露成 AI 能力 |
| A1–A4 | 分层设计、Schema 版本化与迁移 |

原方案覆盖「Chrome 插件核心 API」；加上这两个需求后，还覆盖了「**如何把一个本地工具接入 AI 工作流**」——这在 2026 年是比插件本身更值钱的技能。

## 4. 决策记录

| # | 问题 | 决策 | 状态 |
| --- | --- | --- | --- |
| Q7 | F22 虚拟接口进 MVP？ | **进 MVP** | ✅ 已定 |
| Q8 | L0 Skill 进 MVP？ | **进 MVP** | ✅ 已定 |
| Q9 | 接受 A1–A4 架构预留？ | **接受**，MVP 阶段即按此分层 | ✅ 已定 |
| Q10 | L1 单独做还是并入 L2？ | **并入 L2**，不单独造文件同步机制 | ✅ 已定 |
| Q11 | MCP 读侧默认开还是默认关？ | **默认开**（覆盖了原建议）。补偿措施见下方 4.1 | ✅ 已定 |
| Q12 | 你司响应格式是否统一？ | **不统一**：多为 `{status, message, data}`，经风控等中间层后会变。→ **F24 改为模板库 + 自定义，新增 F25 自动推断**（见 1.5 节） | ✅ 已定 |

### 4.1 Q11 决策的落地方式

读侧默认开启，配套保留两条**不可关闭**的底线（成本极低，且不影响使用体验——AI 不需要真实凭证也能生成 mock）：

| 措施 | 说明 | 可否关闭 |
| --- | --- | --- |
| **强制脱敏** | `Authorization` / `Cookie` / `Set-Cookie` / 常见 token 字段一律打码后再出给 MCP | ❌ 不可关 |
| **域名白名单** | 只有白名单内域名的请求对 MCP 可见，默认只含当前工作域名 | ❌ 不可关，但白名单可编辑 |
| 读侧开关 | 总开关本身 | ✅ 默认开，可手动关 |

> 理由：默认开确实更顺手（vibe coding 时不想每次先去打开个开关）。但「AI 能看到请求」和「AI 能看到你的鉴权凭证」是两件事，前者是产品价值，后者纯粹是负债。脱敏后 AI 依然能看到 URL、参数、响应结构，闭环不受影响。
