# PRD-0003：Mock 工作台可理解性与变体效率

> 类型：PRD
> 状态：In Review
> 更新：2026-08-27
> 依赖：[PRD-0002](./PRD-0002-information-architecture.md)
> 设计评审：[工作台 UI 评审](../../architecture/workbench-ui-review.md)

## 背景与证据

2026-08-27 的两张实际使用截图显示：DevTools 面板把一次请求的历史响应与当前规则内容放在相邻区域，却没有清楚表达时间关系；变体只能回到管理页操作。管理页同时展开项目、规则列表、批量动作、完整编辑表单和响应编辑器，视觉权重接近，扫描成本高。

截图仅作为问题证据，不构成布局或实现指令。

## 要解决的问题

1. 用户无法快速判断正在看的内容是“这次已经发生的响应”还是“下一次请求会使用的配置”。
2. 在 DevTools 排查接口时，切换或新增变体的路径过长。
3. 变体选择保存后没有稳定成为当前生效项，刷新后回到第一项。
4. 管理页低频操作和高频编辑同时暴露，信息密度高但层级弱。

## 统一词汇

| 词汇 | 定义 | 是否可变 |
| --- | --- | --- |
| 请求记录 | 一次已经发生的 fetch/XHR 事件及其元信息 | 否 |
| 本次响应 | 该请求当时实际收到或 Mock 生成的响应快照 | 否 |
| 规则 | URL、方法等匹配条件与响应行为的集合 | 是 |
| 变体 | 同一规则下的一份具名响应定义 | 是 |
| 当前 Mock / 当前生效变体 | 下一次命中该规则时默认使用的变体 | 是 |
| 生成结果 | 模板或动态逻辑在某次请求中求值后的实际 body | 否 |

界面文案不得用“实际返回”指代可编辑规则，也不得只写“规则内容”而不说明它影响的是下一次请求。

## 目标

- 在 DevTools 请求详情内完成变体查看、切换与基于当前内容新增。
- 明确标记请求时变体；当前生效变体变化时保留历史快照，并提示重试后生效。
- 管理页围绕“找到规则 → 编辑当前任务 → 验证”建立主次层级。
- 先修语义、数据和交互结构，再独立评审视觉风格，避免一次改动难以验证。

## 非目标

- 本轮不重做编辑器内核、项目模型或规则匹配算法。
- 本轮不把 DevTools 变成完整管理页；批量导入导出、分组管理仍留在 Options。
- 未通过设计评审前，不实施管理页的大范围换肤或布局重写。

## 用户故事与验收

### US1：理解一次请求

作为正在排障的前端开发者，我能同时看到请求时变体和当前生效变体，知道切换不会改写历史请求。

- Tab 使用“本次响应”和“当前 Mock”。
- 请求记录保存命中时的 `variantId` / `variantName`。
- 两者不一致时明确显示“当前已切换为 …”，并提示重新发起请求。

### US2：快速构造测试状态

作为测试空态、错误态的开发者，我能在请求详情里一步切换变体，或基于当前响应新增变体。

- 切换立即更新规则的 `activeVariantId`。
- 新增变体复制当前响应，生成稳定 ID，并立即激活。
- 刷新扩展或页面后，当前变体保持不变。

### US3：专注编辑规则

作为维护多条规则的开发者，我在管理页只需面对当前任务相关的操作。

- 高频动作常显：新建、搜索、启停、保存。
- 导入、导出、替换等低频动作收进“更多”。
- 编辑器按“匹配 → 变体 → 响应”组织，高级响应设置默认折叠。
- 项目导航可收起；没有项目时不占用持续的大面积空白。

## 分阶段交付

| 阶段 | 内容 | 评审方式 |
| --- | --- | --- |
| A：正确性与语义 | 原子保存变体；记录请求时变体；DevTools 快速切换/新增；统一文案 | 自动测试 + 实际请求走查 |
| B：信息架构 | 管理页命令分层、上下文 Inspector、渐进披露 | 线框图与任务走查 |
| C：视觉系统 | 收敛色彩、状态、密度与请求链路标识 | 明暗主题截图评审 |

阶段 B、C 可独立接受或回退，不阻塞阶段 A 发布。

## 成功指标

- 从选中请求到切换变体不超过 2 次操作。
- 用户无需打开管理页即可建立一个基于当前响应的变体。
- 变体保存/迁移回归测试覆盖“选择非首项”和“新增无 ID 变体”。
- 5 个代表性任务走查中，不再把“本次响应”误认为下一次生效配置。
