# 开发工作流

> 回答一个高频问题：**每次改代码都要重新打包、再去 Chrome 导入一遍吗？**
> 答案是：**不需要**。扩展只需加载一次，之后按下面的流程走。

---

## 0. 最重要的一件事

**加载已解压的扩展程序只需要做一次。**

Chrome 记住的是**目录路径**（`dist/`），不是某个时刻的文件快照。
只要你不删除 `dist/` 目录、不移动项目位置，就永远不用再点「加载已解压的扩展程序」。

之后每次改动，最多只需要点一下扩展卡片上的**刷新 ↻**。很多时候连这个都不用。

---

## 1. 推荐流程：`npm run dev`

```bash
npm run dev
```

它会同时启动两个进程：

| 进程 | 职责 |
| --- | --- |
| `vite`（青色日志） | Popup / Options / DevTools 面板的 HMR |
| `dev:inject`（黄色日志） | 监听注入层源码，重建后自动同步进 `dist/` |

**首次使用**：跑起来之后去 `chrome://extensions` 加载 `dist/` 目录，**这一次之后就不用再加载了**。

### 改了不同的东西，分别要做什么

| 改动位置 | 需要的操作 | 原因 |
| --- | --- | --- |
| `src/hosts/popup/`<br>`src/hosts/options/`<br>`src/hosts/devtools/`<br>`src/ui/` | **什么都不用做** | Vite HMR 直接热替换，界面即时刷新 |
| `src/core/` | 同上（被 UI 引用的部分） | 同上 |
| `src/hosts/inject/` | **刷新目标页面** | 注入脚本在页面加载时执行，必须重新加载页面 |
| `src/hosts/content/` | 刷新目标页面 | 同上 |
| `src/hosts/background/` | `chrome://extensions` 点刷新 ↻ | Service Worker 需要重启 |
| `manifest.config.ts` | 点刷新 ↻ | manifest 变更必须重新注册 |

一句话记忆：**UI 改动零操作，页面脚本刷页面，后台脚本刷扩展。**

### 注入层改动的确认方式

改了 `src/hosts/inject/` 后，终端里会打印：

```
[mock-studio] 注入脚本已更新 —— 刷新页面生效
```

看到这行再刷页面，就不会出现「明明改了却没生效」的错觉。

## 2. 生产构建：`npm run build`

```bash
npm run build
```

比 dev 多做两件事：类型检查（`tsc --noEmit`）和产物压缩。
准备提交代码或想验证真实产物时用它。

构建完同样只需在 `chrome://extensions` 点刷新 ↻，**不用重新加载**。

---

## 3. 为什么注入脚本要单独构建（一个必须知道的坑）

这是本项目构建配置里最反直觉的部分。

CRXJS 默认会把 content script 包成一个 loader，内部用**动态 `import()`** 加载真正的代码：

```js
(async () => {
  const { onExecute } = await import("./index.ts-xxx.js");
  onExecute?.(...);
})();
```

**动态 import 是异步的。** 这会把 hook 的安装时机推迟到模块加载完成之后，
而我们的第一条铁律是「必须在页面任何脚本之前完成 hook」。
一旦推迟，页面早期的请求就会漏拦，**且时序随机、难以复现** —— 这类 bug 极难查。

所以注入脚本走了一条独立管线：

```
src/hosts/inject/index.ts
   │  vite.inject.config.ts（打成同步 IIFE，无 import）
   ↓
public/inject.js
   │  build：vite 自动拷贝
   │  dev  ：由 build/injectContentScriptPlugin.ts 轮询同步
   ↓
dist/inject.js
   │  build/injectContentScriptPlugin.ts 把它写进 manifest
   ↓
manifest.content_scripts[0]  (world: MAIN, run_at: document_start)
```

### 为什么不直接写在 manifest.config.ts 里

写了 `js: ['inject.js']` 的话，CRXJS 会把它当成**源码入口**去解析，
然后报 `Could not resolve entry module "inject.js"` —— 因为它在 `public/` 而不是项目根目录。

所以只能构建后再补进 manifest。

### 曾经踩过的坑

插件最初写了 `apply: 'build'`，导致 **dev 模式下 manifest 里根本没有注入脚本**，
扩展完全不拦截请求，而且**没有任何报错**。现在 build 和 dev 两条路径都覆盖，
并且 dev 下如果 `public/inject.js` 缺失会在终端明确警告。

## 4. 各处的 console 在哪看

改完代码要看日志时，注意**不同脚本的 console 在完全不同的地方**：

| 要看什么 | 打开方式 |
| --- | --- |
| **Service Worker** | `chrome://extensions` → 找到插件 → 点「Service Worker」链接 |
| **注入脚本（MAIN world）** | 网页的 F12 → Console，保持上下文为 `top` |
| **Content Script（ISOLATED）** | 网页的 F12 → Console → **左上角下拉切到插件名**（不切换看不到！） |
| **Popup** | 右键插件图标 → 「审查弹出内容」 |
| **Options 页** | 打开设置页后直接 F12 |
| **DevTools 面板** | **对 F12 窗口再按一次 F12** |

引擎自身状态可以在目标页面的 Console 里直接查：

```js
__MOCK_STUDIO__.stats
// { observed: 37, mocked: 2, rulesLoaded: 5, revision: 8, missedBeforeReady: 0 }
```

## 5. 排错

| 现象 | 解法 |
| --- | --- |
| 改了 UI 没反应 | 看终端 vite 是否报错；HMR 偶尔会失效，刷新扩展页面即可 |
| 改了注入层没反应 | 确认终端有「注入脚本已更新」，然后**刷新目标页面** |
| 页面完全不拦截请求 | 在页面 Console 跑 `__MOCK_STUDIO__` —— 若是 `undefined`，说明注入脚本没加载：检查 `dist/inject.js` 是否存在、manifest 里有没有 MAIN world 条目 |
| Service Worker 显示「已停止」 | 正常现象，30 秒无事件会休眠，有事件自动唤醒 |
| dist 被误删 | 重跑 `npm run build`，然后在 `chrome://extensions` 点刷新（**仍然不用重新加载**） |
| 移动了项目目录 | 这种情况需要重新加载一次扩展 |
