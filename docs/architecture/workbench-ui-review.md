# Mock 工作台 UI 设计评审

> 类型：Design Review
> 状态：Proposed
> 更新：2026-08-27
> 输入：[PRD-0003](../product/prds/PRD-0003-workbench-usability.md)

## 设计判断

这是面向前端工程师的本地调试工作台，不是通用后台。它最重要的任务是让用户在几秒内回答四个问题：发生了什么、命中了哪条规则、当时用了哪个变体、下一次请求会怎样。

当前界面的主要问题不是“组件不够漂亮”，而是所有区域同时争夺注意力：管理页的项目、列表动作、规则表单与 JSON 编辑器等权；DevTools 又把历史事件与可变配置并列但不解释时间线。先修层级，再做视觉润色。

## 方案比较

| 方案 | 结构 | 优点 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| A. 保留固定三栏 | 项目 / 规则 / 完整编辑器始终展开 | 改动最小 | 窄屏拥挤，低频内容长期占位，延续现有问题 | 不选 |
| B. Master-detail + 上下文 Inspector | 可收起项目导航 / 规则工作区 / 仅在选中时出现的 Inspector | 高频路径清楚，适合渐进披露，能复用现有组件 | 需重新分组命令和编辑区 | **推荐** |
| C. 双栏 + 底部编辑抽屉 | 规则列表 / Activity，编辑器从底部展开 | 列表空间最大 | JSON 编辑高度不稳定，键盘与滚动冲突明显 | 备选 |

## 推荐结构

### 管理页

```text
┌ 项目（可收起） ┬ 规则工作区 ───────────────────┬ 规则 Inspector ────────┐
│ 项目 / 未归档   │ 规则  Activity                │ 名称        [保存]      │
│                 │ [新建] [搜索……] [筛选] [更多] │ 匹配条件                │
│                 │                               │ ─────────────────────── │
│                 │ 分组 A                        │ 变体 [正常 ▾] [+]       │
│                 │ ● POST /balance      6 变体   │ 响应定义                │
│                 │ ○ GET  /orders                │ ▾ 高级：头/延迟/行为    │
└─────────────────┴───────────────────────────────┴────────────────────────┘
```

- “更多”承载剪贴板导入、导入并替换、导出等低频动作。
- Inspector 顶部固定名称、状态与保存；正文只显示当前编辑链路。
- “匹配条件 → 变体 → 响应定义”是固定阅读顺序。头、延迟、异常行为放入可展开的高级区域。
- 未选规则时 Inspector 展示简短空状态，不复制全局说明。

### DevTools

```text
┌ 请求列表 ───────────┬ 请求检查 ─────────────────────────────────┐
│ MOCK POST /balance  │ 当前 Mock  [正常-多币种 ▾] [+ 基于当前]   │
│      POST /orders   │ 请求时变体：正常-多币种                  │
│                     │ Request ── Rule match ── Variant ── Result│
│                     │ [本次响应] [当前 Mock]                    │
│                     │ JSON / 当前响应定义                       │
└─────────────────────┴───────────────────────────────────────────┘
```

签名元素是一条紧凑的 **Trace Rail**：`Request → Rule → Variant → Result`。它不是装饰时间线，而是把产品最容易混淆的四层对象固定在同一视觉语法中；错误停在红色节点，当前配置用蓝色节点，历史快照保持中性。第一版可以只做文字和细线，不引入复杂动画。

## 视觉方向：冷静的调试仪表盘

### 色彩

现有蓝紫渐变和大量半透明表面让不同层级相互融合。建议收敛为一主色加三种状态色：

| Token | 建议值 | 用途 |
| --- | --- | --- |
| Ink | `#18202C` | 主文本、关键数据 |
| Canvas | `#F6F8FB` | 页面背景 |
| Surface | `#FFFFFF` | 编辑与列表表面 |
| Signal Blue | `#2563EB` | 当前选择、可执行主操作 |
| Amber | `#B45309` | 变体已切换、需重试 |
| Red | `#C2414B` | 请求错误、破坏性动作 |

渐变不再承担按钮层级；焦点、选择、命中状态用单色和明确边线。暗色主题使用同一语义映射，不单独发明一套颜色。

### 字体与密度

- UI 保持系统 sans 字体，响应体、URL、状态码和耗时使用 `ui-monospace`。
- 默认密度面向 DevTools：行高紧凑但点击区域不低于 28px。
- 标题最多三级；主要依靠字号、字重和间距，不用“框套框”表达层级。

## 两阶段实施边界

### 第一阶段：结构与文案

- 已在本轮完成：DevTools 的“本次响应 / 当前 Mock”、请求时变体、快速切换和新增。
- 下一批：管理页低频动作归入“更多”，高级响应设置折叠，项目栏可收起，Inspector sticky header。
- 保持现有 CSS token，允许只做支撑结构的局部样式。

### 第二阶段：视觉润色

- 经截图评审后替换颜色 token、减少玻璃和渐变、统一状态表达。
- 在 Options 与 DevTools 引入 Trace Rail 的同一套节点语言。
- 分别验证浅色、暗色、DevTools 约 800px 宽和管理页 1280px 宽。

## 评审清单

- 用户能否在 3 秒内指出“本次响应”和“下一次会生效的响应”？
- 窄 DevTools 中切换变体时，响应正文是否仍保有足够宽度？
- 管理页不打开“更多”和“高级”时，是否覆盖 80% 高频任务？
- 颜色移除后，层级是否仍由结构和文字成立？
- 错误、未命中、Mock 命中、变体已切换是否各有唯一且一致的表达？
