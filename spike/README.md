# Spike · 可行性验证

> 目的：在**你司真实业务站点**上验证「MAIN world 注入 hook」这条技术路线走不走得通。
> 这一步不通过，01/02 号文档的方案要重做，所以先做它。
> 预计耗时：**20 分钟**。

---

## 它要验证什么

| # | 验证项 | 不通过的后果 |
| --- | --- | --- |
| 1 | 注入时机够早（赶在页面脚本之前） | 会随机漏拦早期请求，产品不可靠 |
| 2 | 能 hook 到 `fetch` | 拦不住现代请求库 |
| 3 | 能 hook 到 `XMLHttpRequest` | **拦不住 axios**（axios 默认走 XHR） |
| 4 | 能真的**改掉**响应（不只是旁观） | 只能做监控，做不了 mock —— 整个产品不成立 |
| 5 | hook 不会被页面覆盖 | 部分站点上会莫名失效 |
| 6 | MAIN → ISOLATED → SW 通信链路打通 | 数据传不出来，做不了 UI |

---

## 怎么跑

### 1. 安装

1. 打开 `chrome://extensions`
2. 右上角打开 **开发者模式**
3. 点 **加载已解压的扩展程序**
4. 选中 `chrome-mock-extension/spike` 这个目录

### 2. 验证

1. 打开**你司的实际业务站点**（重点：要用真实站点，不要用 demo 页）
2. **刷新一次页面** ← 必须。注入脚本只在页面加载时执行，装插件前就打开的页面不算
3. 点浏览器工具栏里的插件图标
4. 点 **「运行自检」**

### 3. 看结果

弹窗顶部会直接给结论：

```
结论：方案可行 ✓
✓ fetch 拦截并改写成功
✓ XHR 拦截并改写成功（axios 走这条）
✓ 注入时机足够早（页面脚本之前）
✓ hook 未被页面覆盖
```

同时「观测统计」里应该能看到你司站点真实发出的 fetch / XHR 数量在涨。

### 4. 补充验证（可选，但建议做）

在页面 Console 里手动跑一次，看看真实业务请求有没有被观测到：

```js
await __MOCK_SPIKE__.test()
```

再点几下页面上会发请求的功能（列表、搜索、切页），回到弹窗点「刷新统计」，
「详情」区会列出最近 20 条被观测到的真实请求。**确认你司的业务接口出现在里面。**

## 结果怎么判读

### ✅ 全绿

方案可行，进入《技术方案设计》。

### ⚠️ 「注入时已有 N 个脚本执行过」

说明注入晚于部分页面脚本。**不是致命问题**，但要记录下来：
正式产品里如果发现漏拦早期请求，需要考虑补偿手段（比如提示用户刷新页面后再操作）。

### ❌ 「注入脚本没跑起来」

按弹窗提示逐条排查：

| 可能原因 | 怎么确认 | 解法 |
| --- | --- | --- |
| 没刷新页面 | 最常见 | 刷新后重试 |
| Chrome < 111 | `chrome://version` | 升级 Chrome |
| 站点 CSP 阻止 | Console 里有 CSP 报错 | 见下 |
| 企业策略限制扩展 | `chrome://policy` 里有 `ExtensionSettings` | 找 IT 确认 |

> 关于 CSP：`world: "MAIN"` 的 content script **理论上不受页面 CSP 限制**（它由浏览器注入，不是页面加载的脚本）。
> 如果这里真的被 CSP 挡住，基本说明是企业策略层面的限制，那是更硬的问题。

### ❌ 「fetch 成功但 XHR 失败」（或反过来）

把 `详情` 区的完整 JSON 发我，这是引擎实现的 bug，我来修。**这种情况不影响方案可行性。**

### ❌ 「hook 被页面覆盖了」

说明你司站点有代码在重置内置对象（有些埋点 SDK、安全 SDK 会这么干）。
需要针对性对抗（比如用 `Object.defineProperty` 把 `fetch` 锁成不可写）。把站点特征告诉我。

## 代码导读（配合 03 号扫盲文档看）

| 文件 | 世界 | 作用 | 对应知识点 |
| --- | --- | --- | --- |
| `manifest.json` | — | 声明两个 content script，一个 MAIN 一个 ISOLATED | 03 文档 §5 |
| `injected.js` | **MAIN** | 真正 hook `fetch`/`XHR` 的地方；用不了 `chrome.*` | §2 |
| `content.js` | ISOLATED | 中继：接住 `postMessage`，转发给 SW | §2.4 |
| `background.js` | Service Worker | 汇总统计；**状态存 `storage.session` 而非全局变量** | §3.1 §7.1 |
| `popup.js` | 扩展页面 | 用 `chrome.scripting.executeScript({world:'MAIN'})` 一键自检 | §3.4 |

有几处值得对着扫盲文档读的细节：

- `injected.js` 里命中规则时**不调用** `originalSend` / `originalFetch` —— 真实请求根本不发出。这就是「虚拟接口」不会 404、不触发 CORS 预检的原因（02 号文档 §1.2）
- `injected.js` 里用实例级 `Object.defineProperty` 遮蔽 XHR 原型上的只读 getter —— 这是伪造 XHR 响应的标准手法
- `content.js` 里校验 `event.source === window` —— `postMessage` 页面也能伪造，必须验来源（03 号文档 §2.4 的安全提示）
- `background.js` 里 `GET_REPORT` 分支 `return true` —— 异步返回不加这行，`sendResponse` 永远发不出去（§4 的经典坑）

## 注意

- 这是**一次性验证代码**，不是产品代码。验证完就可以删，正式项目会用 Vite + CRXJS + TS 重写。
- 它申请了 `<all_urls>` 权限，会在所有站点注入。**验证完建议在 `chrome://extensions` 里关掉或移除。**
- 它只观测不上传，所有数据留在本地 `storage.session`（浏览器关闭即清空）。
